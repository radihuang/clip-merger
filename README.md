# Clip Merger

手機瀏覽器上的簡易剪片工具：上傳多支影片 → 依拍攝時間自動排序 → 合併成一支，每段秒數可調。

全程在瀏覽器本機處理，影片不會上傳到任何伺服器。

## 現況

| 階段 | 內容 | 狀態 |
|---|---|---|
| P0 | 拍攝時序探針——驗證影片讀不讀得到拍攝時間 | 完成，待實機驗證 |
| P1 | 排序 ＋ 統一秒數 ＋ 合併輸出 | 未開始 |
| P2 | 個別秒數微調、縮圖、進度條、存回相簿 | 未開始 |
| P3 | 部署 GitHub Pages、PWA 安裝 | 未開始 |

P0 先做的原因：整個專案最大的未知數是「使用者的影片到底讀不讀得到拍攝時間」。
這件事決定 P1 的介面設計——讀不到就必須提供手動排序。先驗證再往下做。

## 執行方式

沒有建置流程，不需要 npm。`probe.html` 是自我包含的單一檔案。

- **電腦上看**：用瀏覽器直接開啟 `probe.html`
- **手機上測**：需要透過 HTTPS 網址開啟。目前發佈於 Claude Artifact；
  P3 之後改為 GitHub Pages

唯一的外部資源是 Google Fonts 的字體；連不上網時會退回系統字體，功能不受影響。

## 技術決策

**不用 ffmpeg.wasm。** WebAssembly 線性記憶體上限 2 GB，實務上手機每檔約 100–200 MB
就會爆掉；多執行緒版本需要 `SharedArrayBuffer`，而靜態主機設不了必要的 COOP／COEP 標頭。

**改用 WebCodecs。** 直接呼叫裝置的硬體編解碼器。P1 會引入
[mediabunny](https://mediabunny.dev/)（`dist/mediabunny.min.mjs` 單檔 ESM，
直接放進專案資料夾，仍然不需要 npm）負責 MP4 的解封裝與封裝。

**時間解析自己寫，不依賴函式庫。** mediabunny 的 `getMetadataTags().date` 只讀
`com.apple.quicktime.creationdate` 與 iTunes 風格的 `©day`，
標準 MP4 的 `mvhd` 檔頭時間它刻意跳過（見其 `isobmff-demuxer.ts` 對 `tkhd` 的處理）。
Android 錄的影片通常只有 `mvhd`，所以 P0 自己實作了完整的 box 解析。

## 拍攝時間的四層遞補

排序準確度取決於時間是從哪一層讀到的，介面上每支影片都會標示來源：

| 層 | 來源 | 可信度 |
|---|---|---|
| 1 | `com.apple.quicktime.creationdate` | 最高，含時區。iPhone 原始檔走這條 |
| 2 | `mvhd` 檔頭 creation_time | 可信，但無時區標記，時鐘可能有偏移；同裝置偏移一致，排序仍正確 |
| 3 | 檔名（`VID_20260831_142530` 等） | 推測值 |
| 4 | 檔案修改時間 | 不是拍攝時間，排序不可靠 |

`mvhd` 的時間基準是 1904-01-01 UTC，換算常數 `2082844800` 秒。

## 效能設計

`moov`（中繼資料）在手機錄影檔中通常位於**檔尾**，前面壓著整段影像資料 `mdat`。
探針逐個讀取 top-level box 的 16 bytes 標頭後跳躍定位，只載入 `moov` 本身，
不讀取 `mdat`。實測 1.65 GB 的檔案僅讀取約 1.6 MB。

## 驗證紀錄

`probe.html` 的解析程式已用本機三支真實 MP4 跑過（腳本作法見下方「重跑驗證」）：

- `mvhd` 讀出 `2024-07-04T09:06:12Z`，換算台北時間 17:06:12，
  而檔名為 `170619`——差 7 秒（開始錄影 vs 存檔命名）。
  同時驗證了位元組偏移、1904 紀元常數、時區換算三者皆正確
- `meta/keys/ilst` 路徑成功取出 `encoder` 標籤
- 三支檔案的 `moov` 皆位於檔尾，跳躍定位成功
- `stsd` 的 width/height 偏移為 **+24／+26**（`VisualSampleEntry` 前置
  `reserved(6) + dataRefIdx(2) + preDefined(2) + reserved(2) + preDefined(12)`），
  初版誤寫為 +16／+18，已對照 mediabunny 原始碼修正

**尚未驗證**：iPhone 原始檔的第 1 層路徑。需要實機測試——這正是 P0 存在的目的。

### 重跑驗證

解析程式沒有另外抽成模組，測試腳本用 `node:vm` 直接執行 `probe.html` 裡的
`<script>` 區塊，因此測到的就是網頁實際跑的那份程式碼，不會有兩份實作漂移的問題。

腳本位於 scratchpad（非版控內容），需要時重新產生即可。

## 常見錯誤與處理

**選了影片但顯示「找不到 moov 檔頭」**
檔案不是 MP4／MOV 格式（例如 `.webm`、`.avi`），或檔案損毀。
目前的解析器只支援 ISO BMFF 系列容器。

**所有影片都落在第 4 層「檔案修改時間」**
拍攝時間已被洗掉。最常見原因是選到了經 LINE 轉傳、雲端壓縮或 App 二次匯出的版本，
而不是相簿裡的原始檔。請從相簿直接選取原始錄影。

**時間顯示得出來但比實際早／晚幾小時**
落在第 2 層時會發生，`mvhd` 沒有時區欄位，部分裝置寫入的是當地時間而非 UTC。
不影響排序（同一台裝置的偏移量一致）。

**iOS 上選檔後解析很久或分頁被關掉**
不應該發生——探針只讀檔頭。若真的出現，代表 iOS 在匯出時對檔案做了轉檔。
請回報實際檔案大小與支數。

**字體看起來不對**
Google Fonts 沒載入成功（離線或被擋）。功能不受影響，會退回系統字體。

**「複製診斷報告」沒有反應**
瀏覽器的剪貼簿 API 需要 HTTPS。若是以 `file://` 直接開啟本機檔案會失敗，
改用展開的「原始中繼資料」手動選取。
