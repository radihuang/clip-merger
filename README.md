# Clip Merger

手機瀏覽器上的簡易剪片工具：選多支影片與照片 → 依拍攝時間自動排序 → 各取幾秒合併成一支。
照片可加上平移／縮放動態，不會只是一張不動的圖。

全程在瀏覽器本機處理，影片不會上傳到任何伺服器。

## 現況

| 階段 | 內容 | 狀態 |
|---|---|---|
| P0 | 拍攝時序探針——驗證影片讀不讀得到拍攝時間 | 完成，已實機驗證 |
| P1 | 排序 ＋ 秒數調整 ＋ 合併輸出 | 完成，已實機驗證 |
| P2 | 照片支援＋動態特效＋結尾淡出 | 完成，已實機驗證 |
| P2.1 | 合併前預估檔案大小與過大警告 | 完成，待實機驗證 |
| P2.2 | 合併紀錄（做過哪幾次、用了哪些片段與設定） | 完成，已實機驗證 |
| P2.3 | 調色濾鏡（全域＋單段覆寫） | 完成，已實機驗證 |
| P2.4 | 點縮圖預覽（整支播放＋標出取用段） | 完成，已實機驗證 |
| P3 | 依實測結果調整 | 未開始 |

P0 先做的原因：整個專案最大的未知數是「使用者的影片到底讀不讀得到拍攝時間」。
這件事決定 P1 的介面設計——讀不到就必須提供手動排序。

**P0 實測結論**（6 支影片，iPhone）：iPhone 相簿原始檔命中第 1 層，
`2026-08-14T21:24:50+0800` 帶完整時區；1.2 GB 的檔案原封不動通過，
確認 iOS 匯出時不會轉檔。但下載／轉傳的影片只到第 2 層，
且該時間是平台轉檔當下的時戳、不是拍攝時間 → **因此 P1 保留了手動排序按鈕**。

## 執行方式

沒有建置流程，不需要 npm。

因為使用 ES modules，**必須透過 HTTP(S) 開啟**，直接雙擊 `file://` 會被
瀏覽器的 CORS 政策擋下。

- **本機測試**：在專案資料夾執行任一種靜態伺服器，例如
  `python -m http.server 8000`，然後開 `http://localhost:8000/`
- **手機使用**：GitHub Pages 網址

唯一的外部連線是 Google Fonts 的字體；連不上時會退回系統字體，功能不受影響。

## 技術決策

**不用 ffmpeg.wasm。** WebAssembly 線性記憶體上限 2 GB，實務上手機每檔約 100–200 MB
就會爆掉；多執行緒版本需要 `SharedArrayBuffer`，而靜態主機設不了必要的 COOP／COEP 標頭。

**改用 WebCodecs**（透過 [mediabunny](https://mediabunny.dev/)）。
直接呼叫裝置的硬體編解碼器。

**時間解析自己寫。** mediabunny 的 `getMetadataTags().date` 只讀
`com.apple.quicktime.creationdate` 與 iTunes 風格的 `©day`，
標準 MP4 的 `mvhd` 檔頭時間它刻意跳過（見其 `isobmff-demuxer.ts` 對 `tkhd` 的處理）。
Android 錄的影片通常只有 `mvhd`，所以自己實作完整的 box 解析。

**單次編碼，不做兩段式。** 所有片段畫到同一張 1080×1920 畫布、共用一組編碼器，
時間戳累加。不採「先各自轉檔再拼接」，避免各段編碼參數不一致導致接縫解不開。

**音訊用 `OfflineAudioContext` 渲染整條時間軸。** 各片段依偏移量放入節點，
沒有音軌的片段與照片不放節點、該段自然靜音，同時順便處理不同取樣率的重取樣。
全部接到同一個 `GainNode`，結尾才有辦法一起收掉。

**照片走同一組編碼器。** 逐格把圖畫到同一張 1080×1920 畫布上再送進編碼器，
與影片段落共用時間戳累加，所以照片與影片可以任意交錯而不會有接縫問題。

## 調色濾鏡

每一格照常畫到 2D canvas，再交給一張同尺寸的 WebGL canvas 套 4×5 色彩矩陣，
最後送進編碼器的是 WebGL canvas。預設有原色、黑白、葡萄牙暖黃、暖色、冷色、鮮豔、褪色七種。

操作方式跟照片動態相同：輸出設定裡的「濾鏡」套用到全部片段，
每一列可以單獨改；改全域設定會蓋掉先前的個別調整。影片與照片都適用。
片段縮圖走同一個 shader，看到的顏色就是成品的顏色；合併紀錄存的也是套完濾鏡的縮圖。

**全部是原色時完全不建 WebGL**，合併走原本的 2D 路徑，速度與 P2 相同。
只要有一段用了濾鏡，整次合併建一張 1080×1920 的 WebGL 畫布，之後的合併沿用同一張
（iOS 對同時存在的 WebGL context 數量有上限）。

**GPU 資源被收回時會直接中止。** iOS 記憶體吃緊時可能收回 WebGL context，
之後 `render` 不會丟例外、只會畫出全黑，成品會靜默變成黑畫面。
所以每一格都檢查 `isContextLost()`，一旦發生就中止合併並說明原因。

**葡萄牙暖黃是近似，不是複製。** 目標是 iPhone 攝影風格 Amber 加上
Tone −73、Color 41、Film 10、Grain、白平衡陰天。Apple 沒有公開這些滑桿的算法，
而且攝影風格會分區處理（膚色、天空各自保護）；這裡只能用一個全畫面的線性矩陣，
數值是對著測試色塊調出來的。初版太黃（天空 (120,170,230) 被壓成 (143,172,179) 幾乎變灰），
已收斂到天空 (133,171,198)、膚色 (224,172,140) → (235,171,121)。

**顆粒與檔案大小：iPhone 守得住，桌面 Chrome 守不住。** 顆粒每格隨機，是最難壓縮的內容。
3 秒試片的實際位元率（目標 6.11 Mbps）：

| 環境 | 有顆粒 | 無顆粒 |
|---|---|---|
| iPhone Safari 26.6.1 | 5.20 Mbps | 2.42 Mbps |
| 桌面 Chrome 155 | 10.99 Mbps | 0.12 Mbps |

iPhone 的硬體編碼器守在目標內，使用者肉眼確認顆粒沒有糊成色塊，
所以「預估檔案大小」在 iPhone 上仍是上限，不必為顆粒另外加成。
桌面 Chrome 會超出 80%，選葡萄牙暖黃時預估值會低估——本工具以手機為主，暫不處理。

**不用 `ctx.filter`。** 它是最直覺的寫法，但 iOS Safari 到 27.x 都要手動開實驗功能
「Canvas Filters」才有（caniuse／MDN compat data，2026-10 查證），預設環境下設了
會被靜默忽略——桌面 Chrome 測起來正常，手機成品卻沒有濾鏡，而且不會報錯。
也不用 `getImageData` 逐像素算：每格兩百萬像素，手機上太慢。

**淡出改在濾鏡之後做。**「褪色」會把黑位抬到約 38，淡出若先做，結尾收不到全黑。
shader 裡最後乘上 `1 - 淡出量`。

**探針先行。** 未知數是 iPhone Safari 能不能拿 WebGL canvas 建 `VideoSample`、
以及每格多一道 GPU 處理會慢多少，`filter-probe.html` 只打這兩件事，實機通過後才接進主程式。
探針頁保留著，之後改 `color-filter.js` 可以先在真機上跑一次。

**改 `color-filter.js` 或 `history.js` 要遞增 import 的 `?v=`**，見「常見錯誤與處理」。

## 片段預覽

點片段列左邊的縮圖會開全畫面預覽。影片播整支，進度條上綠色區段是合併時會取用的部分，
「只播取用段」從取用段開頭播到結尾自動停下；點或拖進度條可跳到任意位置。照片顯示原圖。

**預覽是原始畫面，刻意不套濾鏡與照片動態。** 預覽是用來看內容、挑片段的，
成品色調在縮圖上已經看得到；用瀏覽器內建播放器最穩、最省電，也聽得到聲音。
要預覽成品的樣子，影片得逐格送進 WebGL，在 iPhone 上是另一條沒驗證過的路徑。

**取用範圍集中在 `useRange()`。** 目前固定從 0 秒開始；之後做起點選擇只需改這裡，
預覽的綠色區段會自動跟著變。

**停在取用段結尾用 `requestAnimationFrame` 追，不用 `timeupdate`。**
`timeupdate` 大約每 250 ms 才觸發一次，拿來判斷停止點會多播一截。

**關閉時要真的放掉影片。** 只移除 `<video>` 元素不夠，要先清掉 `src` 再 `load()`，
瀏覽器才會釋放解碼器；blob 網址也一併撤銷。合併進行中不能開預覽，避免與編碼搶解碼器。

## 照片動態

照片先以 cover 填滿畫布，再乘一個縮放係數換取可移動的餘裕：

| 特效 | 作法 |
|---|---|
| 緩緩放大 | 縮放由 1.0 掃到 1.18 |
| 緩緩縮小 | 縮放由 1.18 掃回 1.0 |
| 向左／向右平移 | 固定放大 1.35，水平掃過餘裕範圍 |
| 靜止不動 | 純 cover，不做任何運動 |

平移另有單側上限 `OUT_W × 0.25`（270 px）。沒有這個上限時，
超寬照片會在三秒內掃過一萬多像素，看起來像閃過去；
而平移專用的放大係數（1.35）比縮放的（1.18）大，
否則本來就是 9:16 的照片幾乎沒有餘裕可移。

**結尾淡出**只作用在最後一個片段的尾端一秒，用片段內的相對時間計算，
不必仰賴整支影片的預估總長；片段比一秒短時淡出會自動縮短。

## 容量上限

程式本身沒有設任何數量或大小的檢查，實際天花板來自四個地方，
由低到高依序是：

| 限制 | 說明 |
|---|---|
| Web Share | 最先撞到。iOS 未公開數字，幾百 MB 就會丟 `AbortError`；改用「存到『檔案』App」可繞過 |
| 分頁記憶體 | 輸出走 `BufferTarget`（整份在記憶體）＋ fastStart 緩衝 ＋ `new Blob()` 複製，峰值約成品的兩倍。超過會被系統直接中止，沒有錯誤訊息 |
| 照片解碼 | 一張 4000×3000 展開成點陣約 48 MB，與原檔壓縮後大小無關。每張用完立即 `close()`，同時只有一張在記憶體 |
| 輸入檔案數 | 沒有上限，但解析是循序的，數十支會拉長選檔後的等待 |

**輸入檔案的大小幾乎不影響**——影片只讀 `moov` 與用到的那幾秒
（1.2 GB 實測不會整檔載入）。真正決定成敗的是**輸出總長**。

1080×1920 H.264 在 `QUALITY_HIGH` 下是 6.11 Mbps，約每秒 0.73 MB：

| 成品長度 | 檔案大小 | 每段 3 秒約幾段 |
|---|---|---|
| 30 秒 | 22 MB | 10 |
| 1 分鐘 | 44 MB | 20 |
| 2 分鐘 | 87 MB | 40 |
| 5 分鐘 | 219 MB | 100 |

介面會在合併前顯示預估大小，超過 100 MB 轉黃字、250 MB 轉紅字。
門檻換算後分別約是 137 秒與 343 秒。

## 合併紀錄

原本關掉頁面就什麼都不剩，看不到自己做過什麼。現在每次合併成功會自動留下一筆紀錄，
從標題右邊的「做過的紀錄」進去看。

**存的是中繼資料，不是影片。** 一筆紀錄包含：合併時間、成品長度與大小、
每段的檔名／拍攝時間／時間來源層／秒數／特效／濾鏡／有無音軌，以及每段那張 92×164 的縮圖
（有套濾鏡時存的是套完的樣子）。
實測一筆四段的紀錄約 7 KB（縮圖每張約 2 KB）。

**成品影片不留在這裡。** 它在你按「儲存到相簿」時就交給系統了，要看成品請去相簿。
不存影片是刻意的：一支成品動輒幾十到幾百 MB，存進瀏覽器既吃空間，
被系統清除時損失也大。

紀錄只存在這台裝置上，不會上傳，可以單筆刪除或全部清除（清除鍵要按兩下）。

### 紀錄可能會消失

iOS 會在**某個網站連續七天沒有使用者互動**時，把它用 script 存的資料整包刪除——
不是刪一部分，IndexedDB 與 Cache 一起清光。這是 WebKit 的系統政策，不是這裡的設定。

程式在載入時會呼叫 `navigator.storage.persist()` 申請豁免，但 WebKit 依
「是不是主畫面 App」等啟發式決定，**不保證核准**（本機測試環境就沒有核准）。
把頁面加到主畫面並偶爾打開，被清掉的機會比較低。

**紀錄頁會直接顯示目前的申請狀態**（已取得／未取得／瀏覽器不支援查詢），
不必自己去開主控台查——這件事是「申請」不是保證，狀態要看得到才不會誤以為資料一定留得住。

因為存的只是幾 KB 的中繼資料，就算真的被清掉，損失的也只是「我做過什麼」的紀錄，
成品影片在相簿裡不受任何影響。

## 拍攝時間的四層遞補

排序準確度取決於時間是從哪一層讀到的，介面上每支影片都會標示來源：

| 層 | 來源 | 可信度 |
|---|---|---|
| 1 | 影片 `com.apple.quicktime.creationdate`；照片 EXIF `DateTimeOriginal` | 最高。影片含時區，照片若有 `OffsetTimeOriginal` 也含時區 |
| 2 | `mvhd` 檔頭 creation_time | 無時區標記；轉檔過的影片這裡是**轉檔時間不是拍攝時間** |
| 3 | 檔名（`VID_20260831_142530` 等） | 推測值 |
| 4 | 檔案修改時間 | 不是拍攝時間，排序不可靠 |

`mvhd` 的時間基準是 1904-01-01 UTC，換算常數 `2082844800` 秒。

## 效能設計

`moov`（中繼資料）在手機錄影檔中通常位於**檔尾**，前面壓著整段影像資料 `mdat`。
解析器逐個讀取 top-level box 的 16 bytes 標頭後跳躍定位，只載入 `moov` 本身，
不讀取 `mdat`。實測 1.65 GB 的檔案僅讀取約 1.6 MB。

## 驗證紀錄

**解析器**（本機三支真實 MP4）：

- `mvhd` 讀出 `2024-07-04T09:06:12Z`，換算台北時間 17:06:12，
  而檔名為 `170619`——差 7 秒（開始錄影 vs 存檔命名）。
  同時驗證了位元組偏移、1904 紀元常數、時區換算三者皆正確
- `meta/keys/ilst` 路徑成功取出 `encoder` 標籤
- 三支檔案的 `moov` 皆位於檔尾，跳躍定位成功
- `stsd` 的 width/height 偏移為 **+24／+26**（`VisualSampleEntry` 前置
  `reserved(6) + dataRefIdx(2) + preDefined(2) + reserved(2) + preDefined(12)`），
  初版誤寫為 +16／+18，已對照 mediabunny 原始碼修正

**模組抽取**：`mp4-time.js` 是從 `probe.html` 抽出來的。
已寫腳本讓兩份實作吃同一組 10 支檔案，逐欄比對 tier／時間／原始字串／時長／
codec／解析度／旋轉／fps／音訊／標籤鍵，**輸出完全一致**。

**匯入檢查**：15 個 mediabunny 具名匯入全部存在於 bundle 的 `export{}`
（驗證腳本含正對照與負對照，確認 pattern 本身有效）。兩支 module 語法檢查通過。

**P1 實機驗證**（iPhone Safari，2026-09-01）：合併成功，影片成功存入相簿。
WebCodecs 編碼、旋轉校正、封裝與儲存整條路徑均通過。

首次測試時儲存失敗，原因是錯誤處理有缺陷而非功能不通：
`AbortError` 被靜默忽略，使用者按下按鈕看起來「完全沒反應」；
三種不同的失敗又被壓成兩句幾乎相同的訊息，無法從描述判斷是哪一種。
修正後逐一區分 `navigator.share` 不存在、`canShare` 拒絕、`AbortError`、
`NotAllowedError` 與其他例外，並一律附上檔案大小（過大是最常見原因）。

同批修補了 P1 引入的 XSS：影片檔名直接插入 `innerHTML` 未跳脫，
惡意檔名可執行程式碼。已加上 `esc()` 並驗證
`<img src=x onerror=alert(1)>.mp4` 會被中和為純文字。

**P2 EXIF 解析**（本機 11 張真實照片）：檔名日期（`20230428`）與 EXIF
內容（`2023:04:28`）獨立相符，`OffsetTimeOriginal` 的 `+08:00` 也正確換算；
沒有 EXIF 的圖正確回報。另比對「只讀前 512 KB」與讀完整檔的結果一致，
確認這個最佳化不會漏掉 EXIF。

**P2 特效數學**：把 `drawPhoto` 從 `index.html` 抽出來餵假資料跑回歸，
5 種長寬比 × 5 種特效共 25 組，驗證每一格都完整覆蓋畫布（不露黑邊）、
該動的動、該靜的靜。首版沒有平移上限，測出超寬照片三秒內要掃過 10248 px，
補上 `PAN_MAX` 後全部收斂在 126–180 px/秒。

**P2 淡出**：`applyFade` 同樣抽出來測 alpha 曲線——關閉時全程為 0、
尾端一秒由 0 線性到 1、片段短於一秒時自動縮短，共 9 個檢查點通過。

**P2 匯入檢查**：改用實際 `import()` 載入模組來比對（比正則可靠），
19 個匯入全部存在，正負對照均正確。

**P2.1 大小預估**：mediabunny 沒有公開位元率的計算，只能把
`encode.ts` 的 `qualityToBitrateFactor` 與 `computeVideoBitrate` 抄過來。
為了確認沒抄錯，另外照原始碼敘述獨立重寫一份參考實作互相比對，
影片得到 6111000 bps、音訊 128000 bps，兩份完全相同。
**升級 mediabunny 時要回頭核對這段公式有沒有跟著變**，否則預估會靜默失準。

**P2.2 合併紀錄**（2026-09-08，桌面 Chrome 實測，非真機）：
`buildRecord` 抽成純函式後餵假資料跑 17 項回歸（含負對照，確認錯的斷言真的會被記為失敗），
涵蓋照片特效跟隨全域設定與單獨覆寫、Date 轉毫秒、缺時間退回第 4 層、

排序為新到舊、縮圖與設定行正確；單筆刪除、兩段式清除、離開頁面重設清除的預備狀態都驗過。

不是預設值。惡意檔名 `<img src=x onerror=alert(1)>.mp4` 在紀錄頁渲染為純文字，未產生元素。

另檢查 39 個 DOM id 參照在 HTML 中全部存在（含負對照）。

## 常見錯誤與處理

**「做過的紀錄」是空的，但我明明合併過**
最可能是 iOS 把資料清掉了——某個網站連續七天沒開，系統會把它存的資料整包刪除。
另一種可能是用無痕模式開啟，那時 IndexedDB 會被關閉；這種情況進紀錄頁會直接
顯示讀不到的原因，不會假裝沒有紀錄。成品影片在相簿裡，不受影響。

**合併成功，但下面出現「這次沒能寫進紀錄」**
紀錄沒存起來，但影片本身是好的，照樣可以儲存到相簿。
常見原因是裝置空間不足或瀏覽器關閉了網站資料，訊息裡會帶上實際原因。

**開啟後整頁空白**
用 `file://` 直接開檔造成的。ES modules 需要 HTTP(S)，請透過伺服器或 Pages 網址開啟。

**「這個瀏覽器不支援 H.264 影片編碼」**
WebCodecs 的 `VideoEncoder` 不可用。iOS 需要 Safari 16.4 以上，
建議 Safari 26 以上（音訊編碼從該版才完整）。

**所有影片都落在第 4 層「檔案修改時間」**
拍攝時間已被洗掉。最常見原因是選到經 LINE 轉傳、雲端壓縮或 App 二次匯出的版本。
請從相簿直接選取原始錄影。

**時間顯示得出來但比實際早／晚幾小時**
落在第 2 層時會發生，`mvhd` 沒有時區欄位。同一台裝置的偏移量一致，不影響排序。

**下載的影片時間看起來不合理（凌晨等）**
第 2 層讀到的是平台轉檔時間，不是你拍攝或儲存的時間。請用手動排序按鈕調整。

**合併到一半分頁被關掉**
手機記憶體不足。減少片段數或每段秒數，或關閉「保留原音」。

**輸出的影片有黑邊**
片段的長寬比與 9:16 不同。切換到「填滿裁切」可消除黑邊，但會裁掉邊緣。

**「儲存到相簿」失敗**
按鈕會直接說明原因與檔案大小。最常見的是檔案過大導致 iOS 中止分享
（`AbortError`）——減少片段數或每段秒數再合併一次。
或改用「存到『檔案』App」，再從檔案 App 長按該檔案選「儲存影片」移進相簿。

**分享面板出現了，但影片沒進相簿**
面板跳出來之後還要在裡面選一次「儲存影片」；只是關掉面板不會存入。

**重新整理後影片全部不見**
這是預期行為，程式沒有做任何本機保存。選過的片段清單與合併結果都只存在
記憶體（JS 變數與 `URL.createObjectURL` 產生的 blob URL），
重新整理、關閉分頁、或切到別的 App 太久被系統回收，都會整批清空，
必須重新選檔與合併。**已經存進相簿或「檔案」App 的成品不受影響**，
那份檔案已經交給系統了。

**預覽顯示「無法播放這支影片的格式」**
瀏覽器內建播放器不支援這支影片的編碼，常見於桌面 Chrome 播 iPhone 的 HEVC 影片。
預覽用的是播放器，合併用的是另一套解碼，所以合併不受影響。iPhone Safari 不會有這個問題。

**照片顯示「無法解碼這張圖片」**
多半是 HEIC 而瀏覽器不支援。Safari 可以（委派系統 codec），
Chrome／Firefox／Edge 因為沒有 HEVC 授權而完全不能解 HEIC。
請改用 Safari，或在 iPhone 的「設定 → 相機 → 格式」選「相容性最佳」改拍 JPEG。

**照片的時間標示為「檔案修改時間」**
目前只解析 JPEG 的 EXIF；HEIC 的 EXIF 藏在 ISOBMFF 的 `iinf`／`iloc` item
結構裡，是另一條路徑，尚未實作。HEIC 照片會依檔名或檔案時間排序，
需要時請用手動排序按鈕調整。

**照片的平移看起來幅度很小**
本來就是 9:16 的直式照片，cover 之後幾乎沒有多餘畫面可以移動，
只能靠 `PAN_ZOOM` 撐出約 378 px 的行程。橫式照片的平移會明顯得多。

**剛更新完，濾鏡探針整排失敗、畫面全黑或出現 `undefined is not an object`**
瀏覽器拿新頁面配了舊模組。GitHub Pages 回 `cache-control: max-age=600`，
重新整理只會換掉頁面本身，被它 import 的 `.js` 在 10 分鐘內仍用快取。
2026-10-25 實際發生過一次：iPhone 跑新版探針、舊版 `color-filter.js`，
新的呼叫方式被舊函式當成淡出參數，`1 - {}` 得 `NaN`，28 點全部輸出 (0,0,0)。
現在 `color-filter.js` 匯出 `VERSION`，import 端帶 `?v=`，探針一開始就比對，
不符時只會顯示一行「模組是舊版」。**改 `color-filter.js` 時三個地方要一起改**：
`VERSION`、import 的 `?v=`、探針的 `WANT_VERSION`。

**合併時出現「系統收回了 GPU 資源」**
有片段套了濾鏡，合併到一半 iOS 因記憶體不足收回了 WebGL。程式會直接中止，
不會讓你拿到一支黑畫面的影片。減少片段數，或把濾鏡改成「原色」（原色完全不用 WebGL）再合併。

**濾鏡選單是空的，或選了濾鏡畫面沒變**
多半是快取：頁面是新的，`color-filter.js` 還是舊的。等 10 分鐘再重新整理。

**字體看起來不對**
Google Fonts 沒載入成功。功能不受影響，會退回系統字體。
